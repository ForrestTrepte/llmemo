# Test vectors

Shared test cases for the cache format in [../format.md](../format.md) (README
requirement X2). Both the Python and TypeScript test suites must pass all of them.
They're generated by [../tools/generate_vectors.py](../tools/generate_vectors.py); don't
edit them by hand.

All case files are ordinary JSON. Some number literals in them are deliberately written
as floats (`1.0`, `1e-07`), so a Python test sees a `float` where it matters. Parse them
with your language's normal JSON parser.

## keys.json

An array of valid keys. Each case has:

- `input`: the parts a caller passes: `attempt`, `request`, and optionally `label` and
  `variant`.
- `canonical`: the canonical JSON of the key envelope (§2, §3.1), as a string.
- `sha256`: the entry ID (§3.2).

Test: build the envelope from `input`, and check that its canonical bytes equal
`canonical` encoded as UTF-8 and that its ID equals `sha256`.

## invalid-keys.json

Keys that must be rejected. Each case has an expected `error` code, and either:

- `input`: envelope parts with a problem at the envelope level (§3.1), or
- `requestJson`: JSON text to parse with the language's normal parser and use as the
  `request`, with `attempt` 0. If the parser itself rejects the text (JavaScript's
  `JSON.parse` rejects `NaN`), that counts as rejecting it. Otherwise building the key
  must fail with the code given.

Some invalid inputs can't be written as JSON, so each package should test them on its
own:

- Python: a tuple, set, `bytes`, `Decimal`, `datetime`, or enum anywhere in the request;
  a dict with a non-string key; `float("nan")` and `-0.0` passed directly; `True` as the
  attempt.
- TypeScript: `undefined` in an array, a `BigInt`, a `Date`, a `Map`, a class instance,
  and `-0` passed directly. A member whose value is `undefined` is absent, not an error.

## entries/

Each folder is one write case:

- `case.json` holds `key` (the envelope parts), `meta`, and either `reply` or `error`.
  `failureId`, if present, means the case writes a failure record (§5.3) instead of an
  entry. `id` is the entry ID. The expected logical result of reading the entry back is
  `expectedReply` or `expectedError`.
- `cache/` is the complete cache a writer must produce, starting from nothing: the three
  files written when a cache is created (§7.1), plus the entry and its text and vector
  files.

In a `reply`, an object of the form `{"$test.vector": {"dtype": "f64", "values": [...]}}`
is test notation for an array the caller marked as a vector (§4.5). Convert it to
whatever your API uses to mark vectors. It isn't part of the format.

Tests:

1. **Write:** create a cache in an empty folder and record the case. The resulting file
   tree must equal `cache/`: the same file names and identical bytes.
2. **Read:** look up `key` in `cache/`. The result must equal `expectedReply` (or raise
   `expectedError`), and the metadata must equal `meta`. Compare values as JSON values,
   e.g. by their canonical form. For a failure record, the lookup must miss, and reading
   the failure record file directly must give `expectedError`.

## read-ok/

Caches that a reader must accept even though a writer wouldn't produce them, such as
CRLF line endings, other layouts, or text stored inline that a writer would have moved to
a file (§6.2, §4.4). Each `case.json` has `key`, `id`, and `expectedReply`. Look up `key`
in `cache/` and compare the result with `expectedReply`.

## read-errors/

Damaged caches. Each `case.json` has `key`, `id`, `expectedErrorCode` (one of the codes
in §8), and sometimes `limits`, with `entryBytes` and `blobBytes` to set in place of the
default size limits. Looking up `key` in `cache/` must fail with exactly that code.

Each case has exactly one problem, so the error code doesn't depend on the order of the
checks.

Read cases contain only `llmemo.json`, not the `.gitattributes` a new cache gets.
[.gitattributes](.gitattributes) in this folder turns off line-ending conversion, so
cases such as the CRLF one keep their exact bytes in git.
